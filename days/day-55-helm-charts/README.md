## Goal
Package, parameterize, install, upgrade, and roll back complex Kubernetes applications using Helm, the package manager for Kubernetes.

## Time

## Do
Managing dozens of separate YAML files across development, staging, and production quickly leads to configuration duplication and copy-paste errors. **Helm** acts as the package manager for Kubernetes (similar to `apt` for Ubuntu or `pip` for Python). It packages collections of Kubernetes YAML manifests into versioned, parameterized archives called **Charts**.

### Key Helm Terminology

- **Chart:** A bundle of templated Kubernetes YAML manifests and metadata files.
- **Values:** Configuration parameters (`values.yaml`) injected into chart templates to customize deployments per environment.
- **Release:** A specific running instance of a chart deployed into a Kubernetes cluster.
- **Repository:** A shared HTTP server hosting packaged charts (searchable via [Artifact Hub](https://artifacthub.io)).

### Hands-on: Working with Helm

1. Verify or install the Helm CLI on your workstation:
   ```bash
   helm version

   # If not installed on Linux:
   # curl -fsSL -o get_helm.sh https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3
   # chmod 700 get_helm.sh && ./get_helm.sh && rm get_helm.sh
   ```

2. Add a popular public chart repository (Bitnami) and update local indexes:
   ```bash
   helm repo add bitnami https://charts.bitnami.com/bitnami
   helm repo update
   ```

3. Search for available charts:
   ```bash
   helm search repo bitnami/nginx
   ```

4. Inspect configurable parameters of a chart without installing it:
   ```bash
   helm show values bitnami/nginx | head -n 40
   ```

5. Deploy a chart release named `my-web` with overridden parameters:
   ```bash
   helm install my-web bitnami/nginx \
     --set replicaCount=2 \
     --set service.type=ClusterIP
   ```

6. List all deployed Helm releases in the current namespace:
   ```bash
   helm list
   ```

7. Inspect the status, notes, and Kubernetes resources generated by the release:
   ```bash
   helm status my-web
   kubectl get pods -l app.kubernetes.io/instance=my-web
   ```

8. Upgrade the release dynamically to change configuration (e.g., scale replicas to 3):
   ```bash
   helm upgrade my-web bitnami/nginx \
     --set replicaCount=3 \
     --set service.type=ClusterIP
   ```

9. View the revision history of the release:
   ```bash
   helm history my-web
   ```
   Notice revisions `1` and `2` tracked by Helm.

10. Roll back to revision 1:
    ```bash
    helm rollback my-web 1
    helm status my-web
    ```

11. Scaffold a brand-new custom Helm chart to inspect its directory anatomy:
    ```bash
    helm create my-custom-app
    ```
    Explore the generated structure:
    ```
    my-custom-app/
    ├── Chart.yaml          # Metadata about chart name, version, and dependencies
    ├── values.yaml         # Default configuration values for templates
    ├── templates/          # Go-templated Kubernetes YAML manifests
    │   ├── deployment.yaml
    │   ├── service.yaml
    │   ├── hpa.yaml
    │   ├── ingress.yaml
    │   └── _helpers.tpl
    └── .helmignore
    ```

12. Test rendering the chart templates locally without sending anything to Kubernetes:
    ```bash
    helm template test-run ./my-custom-app --set replicaCount=5 | head -n 50
    ```

13. Clean up the release and scaffolded directory:
    ```bash
    helm uninstall my-web
    rm -rf my-custom-app
    ```

## Stretch Goal
Write a custom `values-prod.yaml` file for your scaffolded chart:
```yaml
replicaCount: 5
service:
  type: ClusterIP
  port: 8080
resources:
  limits:
    cpu: 200m
    memory: 256Mi
```
Deploy the chart using the external values file:
```bash
helm install prod-release ./my-custom-app -f values-prod.yaml --dry-run --debug
```

## Common Mistakes
- **Hardcoding values inside `templates/` manifests:** Never hardcode environment-specific IP addresses, image tags, or replica numbers inside `templates/deployment.yaml`. All configurable values should be parameterized via `{{ .Values.myParam }}` and placed in `values.yaml`.
- **Forgetting `helm repo update`:** Unlike package repositories that automatically sync, Helm requires running `helm repo update` before searching or pulling charts, otherwise you will encounter `chart not found` errors.
- **Deleting resources with `kubectl delete` instead of `helm uninstall`:** Deleting pods or services directly bypasses Helm's state tracking. Helm will attempt to manage or recreate them on future upgrades. Always use `helm uninstall <release-name>`.
